## 1. 現状の案の評価

### 1-1. v2までの計画で、良い点（維持する）
- 実績・数値・取引先を捏造しない方針、ロゴの形状を実物から計測して合わせる方針
- 青を「²・主CTA・現在地」に限る色の規律
- PCとSPを同じ構成にそろえ、スマートフォンのメニューやCTAの欠落を直す方針

- 現行案の骨格（10セクション、モノクロ＋青1色、強みの3項目がTRUE/CONSTANT/SQUAREに対応していること）

### 1-2. v2の問題点（改訂する）
| 問題 | 内容 |
|---|---|
| ①「整理」が中心で、勝ち筋が弱い | 装飾を減らして使いやすくする計画で、「よく整理された一般的な制作会社のサイト」で止まるおそれがある。Koto Squareでしかできない体験が、計画のなかに明示されていない |

| ④ アニメーションが多い | オープニング、ロゴ形成、切り替え、ホバー、スクロール連動を「やる前提」で並べていて、必要性と費用対効果を検討していなかった |

## 3. コンペで勝つための差別化

### 3-1. 競合との比較についての注記
**特定の競合サイトを調べたわけではありません。** 以下は、制作会社・BtoBコーポレートサイトによく見られる一般的な傾向（大きな英字タイポグラフィ、ロゴのマーキー、数値カウンター、ローディング演出、横スクロールの実績一覧など）を前提にした整理です。実際の競合や、同じコンペの他の参加者が分かる場合は、ご共有いただければ比較を具体化します。

> 一般的な傾向のなかで埋もれやすいもの：派手な演出、数値の帯、実績のスライダー。
> 一般的な傾向のなかでは希少なもの：**ブランドのロゴそのものが、サイトの仕組みになっている**こと。

### 3-2. 差別化案の比較

| 案 | 内容 | メリット | デメリット・リスク | 工数 |
|---|---|---|---|---|
| **O1 ロゴのシステム化** | ² ＝ 唯一のアクセント、K の斜線 ＝ 区切りと動線の角度、3ピース ＝ 3つの約束。この3つを**ページ全体に一貫したルール**として使う | 低コストで、全ページに効く。「装飾ではなく意味がある」を示せる。モバイルでも安定。信頼感と両立しやすい | 静的なので、それだけでは第一印象のインパクトが弱い | 小 |
| **O2 ヒーローでの形成体験** | 大きなロゴマークが、3ピースから K として組み上がり、² が置かれる。TRUE → CONSTANT → KOTO² を、ユーザーの操作で切り替えて見られる | 最初の画面で、ブランドの考え方が**動きとして**伝わる。審査員の記憶に残りやすい | 作り込みが必要。自動切り替えにするとアクセシビリティの問題が出る（手動切り替えなら回避できる）。SPでは大きさの調整が必要 | 中 |

| **O4 コピーとタイポグラフィ主導** | 「何度でも²」という言葉の構造（反復）を、見出しや文章のリズムで見せる | 低コスト。動きに頼らない | コピーが評価の大部分を占める。**コピーの確認（依頼者の承認）が必要** | 小 |

| **O6 診断ツール型** | 「あなたの課題はどの領域か」を、質問で導く | 問い合わせ獲得に直結しうる | **サービスの判断基準を推測で作ることになり、禁止事項に近づく**。工数も大 | 大 |

### 3-3. 推奨案

**「ロゴをサイトの仕組みにする（O1）」を土台にし、ヒーローに1つだけ印象的な場面（O2）を置く。O4を軽く添え、O3は余裕があれば縮小版で検討する。O5とO6は採用しない。**

構成する要素：

1. **² は、唯一のアクセントとして使う（O1）**
   青い正方形は、「次の一歩」を示す箇所にだけ現れる（主要CTAの印、現在地の印、見出しの終わりの ²）。装飾には使わない。
2. **Kの斜線の角度を、ページの区切りと動きの角度にする（O1）**
   背景のセクション境界、ボタンのホバー、画像の切り抜きに、ロゴの斜線の角度（上の線：約31.5°、下の線：約41° — 第5章の注記を参照）を使う。
3. **3つのピースを、3つの約束に対応させる（O1・O2）**
   TRUE／CONSTANT／SQUARE の強み3項目と、ロゴの3ピースを対応させる。**この対応づけ自体が、私たちの解釈であり、依頼者の確認が必要です**（第9章）。
4. **ヒーローに、ロゴが組み上がる場面を1つだけ置く（O2）**
   ページを開くと、内容はすぐ読める状態で、マークが約1秒で K として組み上がり、² が置かれる。その後は、ユーザーが操作して TRUE → CONSTANT → KOTO² の見え方を切り替えられる（自動では切り替えない）。
5. **それ以外の動きは静かにする**
   「1か所だけ目立たせ、あとは静か」にすることで、信頼感と記憶への残りやすさを両立する。

### 3-4. 審査員の記憶に残る要素（推奨案が目指すもの）
- **「ロゴの形（K）が、そのままサイトの考え方になっている」という一貫性**
- 最初の画面で見られる、**ロゴが組み上がる1つの場面**
- **青が ² にしか使われていない**という、徹底した規律

### 3-5. 新しさと信頼感の両立のルール
1. 動きは、ブランドの考え方を伝えるものにだけ使う。
2. 内容（文章、CTA、情報）は、動きより先に読める状態にする。
3. 動きは、1か所ごとに目的を説明できるものだけにする。
4. 信頼に関わる部分（会社情報、問い合わせ）は、動きを加えず、確実に読める状態にする。

## 4. 実績・会社情報の見せ方

### 4-1. 原則
1. **実在しない企業名、ニュース、導入事例、成果数値は作らない。** 「[クライアント名]様」のような括弧つきの仮表示も使わない。
2. **確認できていない情報は、表示しない。** 空欄や仮の値で埋めない。
3. 見本が必要な場合は、**内容を持たない骨組み**（グレーの枠だけ）で示し、**常に見える注記**を付けて、実在の内容ではないことを明示する。
4. 代表者の写真やプロフィールは、**掲載の許可を確認してから**採用する。

### 4-2. コンペ提出版と公開版の区別

| 項目 | コンペ提出版（モックアップ） | 公開版（実際のサイト） |
|---|---|---|
| 目的 | レイアウトとブランド表現の評価 | 事実だけを載せる |
| 制作実績 | 第4-3章のいずれかの方法 | **実績が1件確定し、掲載許可を得るまで非表示**（ナビの項目も非表示） |
| ニュース | 同上 | **実在するお知らせが出るまで非表示** |
| 会社概要 | **確定した行だけ**表示 | 確定した行だけ表示。必須の項目（代表者・所在地など）が揃ってから公開 |
| 代表者の情報 | 掲載許可が確認できるまで使わない | 同左 |
| 資料ダウンロード | PDFが存在しない場合は、ボタンを表示しない（代わりのボタンは第6章） | 同左 |
| 問い合わせフォーム | デザインとして表示する。**送信されないデモであることを注記する** | 実際の送信先を接続してから公開 |
| 見本であることの表示 | 見本のブロックに、常に見える注記（例：「デザイン見本 — 実際の掲載内容ではありません」） | 見本のブロックは**存在しない** |

### 4-3. 制作実績・ニュースの見せ方（コンペ提出版）
この2つは「必須の10セクション」に含まれるため、コンペの提出物で消してよいかが重要です。

| 方法 | 内容 | メリット | デメリット |
|---|---|---|---|
| (a) ページ内に骨組みで表示 | 内容を持たないグレーの枠と、1行の注記だけを置く | 構成が欠けて見えない | 骨組みだけのため、中身が薄く見える |
| (b) TOPからは外し、別ボード（付録）に示す | 「運用開始後のレイアウト案」として、別に掲載する。TOP本体は確定した情報だけで構成する | 本体の完成度が高く保たれ、誤解も生じない | 「必須項目の欠落」と見なされる可能性がある |

**推奨：コンペの必須項目に「制作実績」「ニュース」が含まれていれば (a)、含まれていなければ (b)**。この判断には、依頼者が指定した必須項目の一覧が必要です（第9章 ①）。

### 4-4. 実績がなくても信頼感を伝える構成
推測を含まず、確認できた事実だけで構成します。

1. **一貫性**：ロゴ、色、コピー、動きが同じ考え方でそろっていること自体が、信頼感の土台になる
2. **明確さ**：何の会社か、何を相談できるかが、最初の画面で分かる（確認できた事実だけで記述）
3. **誠実な文章**：断定や最上級の表現を避け、できることだけを書く
4. **連絡先の確実さ**：問い合わせの手段が、迷わず見つかり、確実に届く
5. **人の見える情報**（掲載の許可が確認できた場合のみ）：代表者の名前、写真、ひとこと
6. **会社概要の確かさ**：確定した行だけを、整った見た目で示す。行が少なくても、配置を整えれば未完成には見えない

### 4-2補足. 強みの文言について
原案の強み3項目（「根拠のある方法だけを提案します」など）は、**その会社が実際に行っている実践の約束**にあたります。依頼者に事実かどうかを確認するまで、「確認待ちのコピー案」として扱い、公開版には載せません（第9章）。

## 5. デザイン・ブランド・アニメーションの方針

### 5-1. ロゴの形状についての訂正
v1・v2で「Kの2本の斜線は平行」と書きましたが、**誤りでした**。実物のロゴを計測した結果：
- 上の白い斜線：右上から左下へ。水平に対して**約31.5°**（横16.3 : 縦10）
- 下の白い斜線：中央付近から右下へ。水平に対して**約41°**（横11.5 : 縦10）
- 2本は、中央付近でつながる「く」の字（Kの腕）の形をしており、平行ではない

これは**PNG画像からの計測値**です。正式なロゴデータ（SVG等）が入手できれば、それを正とします。ピースの座標（`HANDOFF.md` 第4章）は、最終的に重ねて確認します（第10章）。

### 5-2. デザインシステム（v2を維持し、簡素化）
- **色**：インク（#111114）、本文グレー、補助グレー、線、薄い背景、青（#1E3CFF）の約6色
- **青の用途**：² ／ 主要なCTA ／ 現在地。それ以外には使わない
- **文字サイズ**：8段階程度。行間は本文1.8、見出し1.3〜1.5
- **余白**：8pxを基準
- **コンテンツ幅**：1200px（本文）、最大1360px
- **ボタン**：主（黒）／副（枠線）の2種類。高さは、PC 56〜64px、SP 56px
- **カード**：枠線1pxで、影は使わない（ホバー時のみ軽い影）
- **セクション見出し**：「小ラベル＋見出し」の1種類に統一。小ラベルの四角は、² のルールに従い、**使うなら ² の意味があるときだけ**にする

### 5-3. アニメーションの採否（必要性・効果・負荷・工数で判断）

| 動き | ブランドの伝達 | 問い合わせ・理解への貢献 | 速度・操作性・SPへの影響 | 工数に対する効果 | **判断** |
|---|---|---|---|---|---|
| オープニング（全画面の演出、約4秒） | 中 | **マイナス**（本文とCTAを待たせる） | 悪い（初回表示の遅れ、毎回再生） | 低 | **不採用** |
| ヒーロー内のロゴ形成（約1秒、内容は先に表示） | **高** | 中立（待たせない） | 良い（transform と opacity のみ） | **高** | **採用（A）** |
| TRUE → CONSTANT → KOTO² の切り替え（手動） | **高** | 小 | 良い（手動のため操作性が高い） | 中 | **採用（B）** |
| ヒーローの自動切り替え | 中 | マイナス（読んでいる途中で変わる） | アクセシビリティの課題 | 低 | **不採用** |
| CTAのホバー（斜線に沿ったスイープ） | 中（斜線の角度） | 小（押せることが分かる） | 軽い | 中 | **採用（B）**。基本のホバー状態はAで実装 |
| サービスカードのホバー | 小 | 小 | 軽い（SPでは不要） | 低〜中 | **簡素に採用（B）** |
| スクロールでの出現（フェード、24px以下） | 小 | 小 | 軽い（非対応でも表示される） | 低 | **採用（B）** |
| スクロールでKが組み上がる（O3） | **高** | 小 | 負荷あり | 低〜中 | **余裕があれば縮小版（B）** |
| 取引先のマーキー | なし | なし | 常時動く | なし | **削除** |
| 巨大な縁取り文字のパララックス | なし | なし | 負荷あり | なし | **削除** |
| 見出しの帯によるカバーリビール | 低 | なし | 読み始めが遅れる | 低 | **削除** |
| 矢印のロール、進捗バー | なし | なし | 常時動く | なし | **削除** |

**共通ルール**：動きは `transform`・`opacity` を中心にする。JavaScriptが無効、または動きを減らす設定の場合は、ロゴは完成形で静止し、すべての内容がすぐ表示される。

### 5-4. スマートフォンの方針（v2を維持）
- 同じコードで全画面幅に対応（390 / 768 / 1024 / 1280 / 1440）
- ヒーローの順序：コピー → 説明 → CTA → ロゴ。CTAを最初の画面に入れる
- メニューは全画面で開閉でき、キーボードにも対応する。追従CTAは、ヒーローを過ぎてから表示する
- 44px以上のタップ領域。ホバーでしか見えない情報は作らない

## 6. 問い合わせ導線の改善案

### 6-1. 設計の考え方
CTAを増やすのではなく、**「読んだ直後に、迷わず進める」構造**にします。実際のサービス内容や相談の流れは、**確認できていない事実を推測で作りません**。

### 6-2. 各要点への対応

| 要点 | 方針 | 未確認のため保留する部分 |
|---|---|---|
| 最初の画面で「誰に何を」伝わるか | 「何を」：事業内容の1文。**依頼者が事業内容として確認した記述に限る**。「誰に」：対象の顧客像が確認できるまで書かない。ヒーローのコピーには、**対象を差し込める位置を設計だけしておく** | 顧客像、事業内容の正式な文言 |
| 4事業を自分事として理解できるか | 4つのカードに、**「この領域で相談する」ボタン**を付ける（相談の入口にする）。「こんな課題に」の例文は、**依頼者が確認するまでコピー案扱い**で、公開しない | 各事業の課題例、対象 |
| サービスの直後に相談へ進めるか | サービス一覧の直後に、相談への導線（CTA）を置く。ボタンを押すと、**問い合わせフォームの「相談内容」が、その事業に選択された状態**で開く（これは仕組みであり、事実ではない） | なし |
| 無料相談で何ができ、相談後に何が起きるか | **確認できているのは「無料」ということだけ**（依頼者のCTA名より）。それ以外（内容、所要時間、対応期限、費用、相談後の流れ）は、**確認できるまで書かない**。確認できた時点で、3ステップなどの形で追加する | 相談の内容、流れ、返信の期限 |
| 連絡先・フォームが未確定の場合 | 下の6-3のとおり | 問い合わせの受付手段 |

### 6-3. 問い合わせ手段が未確定の場合の進め方
1. **フォームの項目は、設計として決められる**（お名前、会社名、メール、相談内容の領域、内容、同意）。これは事実ではなく、デザイン上の選択
2. **コンペ提出版**では、フォームを表示し、「デモです。送信されません」と常に見える注記を付ける
3. **公開版**では、確認できた受付手段（フォームの送信先、メール、電話）に実際につなげてから公開する。つながっていない状態では公開しない
4. 返信の期限（原案の「3営業日以内」）は、**確認できるまで書かない**
5. プライバシーポリシーは、フォームを公開するために必要。存在するか、誰が用意するかを確認する

### 6-4. 資料ボタンの扱い
依頼者のCTAは2つ（「無料で相談する」「会社資料をダウンロード」）ですが、**PDFの有無が未確認**です。
- PDFがある → 2つ目のCTAを、そのまま「会社資料をダウンロード」にする
- PDFがない → 2つ目のCTAは**出さない**（1つだけにする）か、「サービスを見る」（ページ内リンク）に置き換える。**どちらにするかは依頼者の判断**
- 依頼者に、「簡易な会社資料（PDF）を用意できるか」「その内容は何か」を確認する。実在しない資料を、あるように見せることはしない
- 設定の仕組みは作らない。制作時点で確認できた状態に合わせて、1回だけ決める

### 6-5. CTAの配置（最小限）
ヘッダー、ヒーロー、サービス一覧の直後、問い合わせセクションの4か所。SPでは、ヒーロー通過後に追従する1つの相談ボタンを加える。

## 7. 実装方法の比較

### 7-1. 現時点の結論：**決めない（保留）**
コンペの提出形式が未確認のため、最終決定は保留します。第9章 ①で確認します。

### 7-2. 条件ごとの適性

| 提出形式・条件 | 適している方法 | 理由 |
|---|---|---|
| 動くURLでの審査、実機（PC・スマートフォン）で操作して評価される | **HTML** | 動き、レスポンシブ、操作性を、実際の環境で評価してもらえる |
| 静止画・PDF・デザインデータでの審査 | **キャンバス（デザインデータ）** | 見た目の比較が中心。実装の工数を、デザインの磨き込みに使える |
| 動きの質が評価対象に含まれる | HTML | キャンバスでは、動きの再現に制約がある（追従ボタン、初回だけの演出、動きを減らす設定など） |
| 締切が短い | キャンバス | 移植の工数が不要 |
| 受注後に、そのまま実装へ進む | HTML | キャンバスのままでは公開できず、作り直しが必要になる |
| PCとSPを並べて見せたい | キャンバス（または、HTMLから書き出した画像） | 並べて見せるのに向いている |

### 7-3. 両方を用意する場合
| 観点 | 内容 |
|---|---|
| メリット | 動く版と、並べて見せる版の両方で、強みを出せる |
| 追加工数 | **HTMLを元にして、スクリーンショットから静止画ボードを書き出す場合は、小さい**。逆に、キャンバスから HTML を作る場合は、大きい |
| リスク | 2つの版の内容がずれる（どちらが正か分からなくなる）。**元になる版を1つに決める**ことで避ける |
| 方針 | 両方が必要になった場合、**HTMLを元にして、静止画を書き出す**のが効率的 |

### 7-4. Claude Codeで実装する場合
| 観点 | 内容 |
|---|---|
| 保守性 | 1つのコードで、PCとSPの両方に対応できる。色、文字サイズ、余白をCSS変数でまとめられる。ただし、**運用機能（データ管理、CMS）は、必要性が確認できるまで作らない** |
| レスポンシブ | 実際のブレークポイント（390 / 768 / 1024 / 1280 / 1440）で確認できる |
| 動作確認の方法 | ChromiumでPlaywrightを使い、各画面幅のスクリーンショット、動きを減らす設定のエミュレーション、JavaScript無効時の表示、キーボード操作、操作の実行を確認する。**ロゴのSVGは、元のPNGと重ねて、ずれを数値で確認する** |
| Safari | **この環境ではChromiumしか使えない**。WebKitが導入できるかは未確認。Safariの最終確認は、**依頼者のiPhoneまたはMacでの確認が必要** |

### 7-4補足. 形式に関係なく、先に進められる作業
提出形式が決まる前でも、次は**どちらの方法でも使える**ため、先に進められます。
- ロゴのSVG座標（キャンバスにも、HTMLにも、そのまま使える）
- デザインのルール（色、文字、余白）
- 情報の整理（確認できた情報／できていない情報の台帳）
- コピー案と、ページの構成
